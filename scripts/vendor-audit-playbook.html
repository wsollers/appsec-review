Process guide + copy-paste prompt library

A playbook for auditing a polyglot vendor codebase with an LLM in the loop

This is built for the review you described: Unity/C# client, C++ game server, Python and Go utilities, Packer/Terraform infrastructure, and a PHP 5 + MySQL backend, delivered by a vendor in China, for a mobile game with real players and real player data. Every phase below pairs a short rationale with a prompt block you can paste into a frontier model, plus notes on what should never touch the LLM raw and should instead be pre-processed by a tool first.

The core discipline: tools produce evidence, the LLM reasons over evidence, humans verify conclusions. Nothing below asks the model to "read the codebase" unstructured — every prompt tells it what artifact to consume and what shape to return.

OP

Where I'd change your plan

You asked for opinions, not just prompts. Here's what I'd add, reorder, or do differently before you start.

Reorder: threat model before ASVS execution, not after

Your outline was discovery → ASVS partition → ASVS run. I'd insert threat modeling as its own phase between the two, using the discovery inventory to build trust boundaries and attacker entry points before you run ASVS controls against the code. ASVS testing without a threat model turns into a checklist exercise — you verify controls exist without knowing which ones actually sit on an attack path. With the threat model done first, Phase 4's assessment prompts can say "this endpoint is reachable from an untrusted client across trust boundary B2" instead of grading every control as equally important.

Add a tooling pre-pass before any LLM discovery prompt

Don't hand a frontier model a raw file tree and ask it to classify a multi-language, multi-hundred-thousand-line vendor drop from scratch — it will miss files, hallucinate structure, and burn context re-deriving things a five-minute tool run gets exactly right. Run cloc/scc, a secrets scanner, an SBOM generator, and SAST tools first, then feed the LLM their structured output (JSON/CSV/SARIF) to classify and interpret. This is Phase A below and it's the single biggest change I'd make to your plan — it's also what makes the rest of the pipeline scale past a toy-sized codebase.

Add a dedicated vendor-trust / supply-chain workstream

Because this code ships from a vendor rather than being written in-house, you have a category of risk ASVS doesn't cover well: silent update mechanisms, opaque native plugin binaries, outbound "phone-home" telemetry to endpoints you don't control, embedded state-mandated cryptography (SM2/SM3/SM4 substitutions occasionally show up in vendor-supplied crypto that has to satisfy Chinese commercial cryptography regulation — worth understanding, not automatically a finding, but worth knowing it's there), and license/IP provenance for anything that looks copy-pasted rather than authored. I've folded this into Phase 1B and flagged it distinctly rather than burying it inside generic ASVS communication/config checks — you want an executive who reads this report to see "vendor trust" as its own risk axis, separate from "this input isn't validated."

ASVS is thin on native memory safety and has nothing on game-specific trust

ASVS is a web/application-layer standard. Your C++ game server has a whole risk class — buffer overflows, use-after-free, integer overflow in packet parsing, double-free, race conditions in shared game state — that ASVS's "Validation, Sanitization and Encoding" chapter gestures at but doesn't operationalize. Same for game-specific trust: anti-cheat bypass, IAP/economy fraud, matchmaking abuse, save-state or asset-bundle tampering — none of that is in ASVS at all. Rather than force-fitting these into ASVS categories (which produces awkward, unconvincing mappings), I've given them their own supplemental checklists driven by CWE/SEI CERT C++ and a short custom "game trust" list (Phase 4B/4C). Track them as first-class alongside your ASVS chapters, not as ASVS footnotes.

PHP 5 is a finding before you look at a single line of application code

PHP 5 reached end-of-life in January 2019 and has received no security patches since — no CVE fixes, no engine-level hardening, nothing. Flag "unsupported runtime, PHP 5.x" as a standing Critical/High finding independent of whatever the ASVS configuration chapter turns up, because it changes the entire risk calculus for that component: any RCE-class bug found in the PHP engine itself after 2019 is permanently unpatched on this stack. Treat modernization to a supported PHP 8.x line as the headline remediation item for the backend component, not a line item buried in a findings table.

Verify CVEs by reachability, not by presence

A dependency scanner will return hundreds of CVE hits across a codebase this size, and most will be in code paths that are never called, in dev-only tooling, or in transitive dependencies pulled in for one unused function. Don't report "347 known CVEs" — that number is meaningless and will get the report ignored. Build a reachability tier: Confirmed-reachable (the vulnerable function is in your call graph and reachable from an untrusted input), Present-unreachable (dependency is used, vulnerable code path is not), Present-unused (dependency imported but the vulnerable module isn't referenced at all). Phase 5 below is built around this triage, using the LLM to do the reachability judgment call once you've handed it the call site and the vulnerable function's signature from the advisory.

What to run outside the LLM, full stop

Anything deterministic, anything that needs to enumerate every file without sampling, and anything requiring bit-exact parsing (binary formats, ASN.1, IaC state files) belongs to a tool, not a model context window. Concretely: secrets scanning, SBOM/license generation, dependency CVE lookups, IaC misconfiguration scanning, C/C++ static analysis for memory safety, and code-size/complexity metrics should all run as tools and get fed to the LLM as evidence. What the LLM is genuinely good at and tools aren't: business-logic reasoning ("does this authorization check actually cover this code path"), synthesizing a threat model narrative, drafting remediation guidance in plain English, and triaging reachability/severity once given the raw facts. Match the phase to the tool that's actually better at it — see Phase A for the specific tool list.

Don't skip COPPA / age-appropriate design for a mobile game

You listed GDPR — correct, and given the vendor is China-based, also consider PIPL (China's Personal Information Protection Law) for any data that transits or is stored on vendor-controlled infrastructure. But mobile games routinely attract under-13 (COPPA, US) and under-18 (UK Age Appropriate Design Code, EU DSA minor-protection provisions) players regardless of intended audience. If there's no active age-gating or the game's genre/marketing skews young, add a data-protection-for-minors pass to Phase 2D — it changes what "excessive data collection" means and what consent flow is even legal to ship.

Make the markdown finding format machine-parseable from the start

Free-form markdown with prose severity ratings is a pain to convert to SARIF reliably. Use YAML frontmatter per finding (schema in Phase 6) so the conversion script parses structured fields instead of pattern-matching prose. This costs nothing extra to produce and turns the SARIF step into a 100-line deterministic script instead of a regex minefield.

Code indexing: tree-sitter, ctags, and where LSIF/SCIP fit

The Phase 5 CVE-reachability prompt needs actual call sites, and the Phase 1 discovery prompt is far more reliable when it's handed entry points instead of asked to find them. Three tiers, cheapest to most exact:

TierToolWhat it gives youWhat it can't do
Tag indexuniversal-ctagsA fast, per-language "jump to definition" tag file — cheap, near-zero setup, good for a human doing manual review alongside the LLM outputNo call graph, no cross-file resolution
Syntax-level symbol/call indexbuild_symbol_index.py (tree-sitter, delivered with this playbook)Per-file JSON of function/class definitions and candidate call sites by name, across C#, C++, Python, Go, PHP, plus a structural pass over Terraform blocks — this is what feeds Phase 1 and Phase 5 belowName-based matching only — no overload resolution, no dynamic-dispatch resolution, no cross-file symbol binding. Treat its call list as "candidates to verify," not ground truth
Semantic index (LSIF / SCIP)Per-language: Roslyn workspace analysis for the Unity C# project, gopls-based indexing or golang.org/x/tools/cmd/callgraph for Go, a real Python language server (pyright/jedi) for the utilities, a Joern Code Property Graph for the C++ game serverAn exact, semantically-resolved call graph — the right evidence to cite when a Phase 5 reachability verdict actually matters for the reportNeeds the target repo's real build environment to resolve symbols correctly (Unity's package cache, the actual go.mod/module graph, a Python venv with the project's real dependencies) — this is why it isn't baked into the generic toolbox image below. Build these per-component, once you know the build actually resolves, and drop their output into the same evidence tree

Practical sequencing: run the tree-sitter index for everything, cheaply, in the pre-pass. Reach for a real Joern/LSIF/SCIP build only for the specific component a Phase 5 "Confirmed-Reachable" verdict hinges on — that's usually a handful of call sites in the C++ game server or a backend service, not the whole codebase.

Why Joern, not CodeQL, for the C++ semantic layer

CodeQL is the more famous option here and it's tempting to reach for it first, but it's wrong for this specific engagement for two independent reasons, not just one. First, licensing: the CodeQL CLI's terms restrict use to open-source and research code without a GitHub Advanced Security subscription — this is vendor-owned proprietary code, so that doesn't clearly cover this use. Second, and this is the one that would bite you even if licensing weren't a concern: CodeQL's C/C++ extractor needs the code to actually build to produce a full-quality database. --build-mode=none exists but gives a materially weaker extraction for C/C++ than a real compile — and a vendor-delivered game server building cleanly, from scratch, in your review environment, with no build-system archaeology, is not a given. Joern doesn't have either problem: it's genuinely Apache-2.0, and its fuzzy parser is designed to degrade gracefully without a full build. Use ast-grep and weggli for fast, hypothesis-driven structural queries, and reach for Joern when a hypothesis needs a real taint/dataflow answer rather than a pattern match.

Semantic retrieval layer (vector search over the codebase)

Everything above is exact — definitions, call sites, structural patterns. It all requires knowing roughly what you're looking for. The gap that leaves open: Phase 4's ASVS-assessment prompts need you to curate which files/functions go with which chapter, and on a codebase this size, hand-curating "everything touching session tokens" across five languages is slow and lossy. build_semantic_index.py and query_semantic_index.py (delivered alongside this page) close that gap with a small retrieval-augmented-generation layer:

  1. Read the per-file JSON build_symbol_index.py already produced, and chunk each source file at its actual function/class boundaries — not arbitrary line windows.
  2. Embed every chunk with an open, code-aware embedding model, run locally via fastembed (ONNX-based — no multi-gigabyte torch install, which matters when this needs to run in a constrained build environment). Default model: jinaai/jina-embeddings-v2-base-code, a real currently-available open-weights code embedding model — swappable via a CLI flag, since this specific ranking shifts and shouldn't be hardcoded into a playbook.
  3. Store chunk text + metadata (path, language, definition name, line range) + vector in a LanceDB table — embedded and file-based, so it lives in the /evidence tree like everything else here, no server to stand up or maintain. (If this stops being a one-off engagement and becomes a standing internal tool multiple analysts query concurrently across many vendor audits, Qdrant is the better call at that point — it's a real service with mature filtered search. Skip Milvus either way; it's built for distributed, billion-vector scale that a single codebase, even a large one, doesn't approach.)
  4. Query it in plain language and get back ranked code chunks to attach as evidence to a Phase 4/1B/6 prompt, instead of a manually assembled file list.

What this is (and isn't) trustworthy for

Semantic similarity is a recall tool — it tells you what to hand the LLM, not a fact you can cite. Keep it out of Phase 5 reachability verdicts and out of the finding schema's location field; that stays on the structural/call-graph side (build_symbol_index.py, ast-grep, Joern). Tested end-to-end against a small synthetic multi-language sample: querying "client-supplied currency balance trusted without server check" correctly surfaced a C# ApplyBalance method assigning a client-supplied value straight to the wallet, ranked above unrelated code — the exact Phase 4C pattern this playbook flags as a presumptive Critical/High finding. Querying "IAP purchase receipt verification" correctly surfaced the Python receipt-validation function over a logging function in the same file. Retrieval quality tracks the embedding model and chunking strategy, not magic — validate it against a handful of known-location queries on the real codebase before trusting it for evidence selection at scale.

Prompt 1A — Component & data-flow discovery

Run once per location (Client / Game Server / Backend / Cloud-Infra) to keep context manageable
You are performing application-security discovery on one location-slice of a larger vendor-delivered codebase. Do not read or summarize raw source files from memory or assumption — work only from the evidence attached below.

CONTEXT
- Product: mobile game. This slice: {{LOCATION}} (e.g. "Game Server, C++").
- Vendor: third-party development shop based in China; this code was delivered, not written in-house.
- Attached evidence: (1) `scc`/`cloc` output for this location, (2) file tree with directory-level comments if any exist, (3) relevant SAST tool JSON already scoped to this location, (4) dependency manifest(s).

TASK
Using only the attached evidence and files you are given direct excerpts of (ask for specific files by path if you need to see one before classifying it — do not guess its contents):

1. Produce a component inventory table with these exact columns: component_id, name, location, language, function_tags (comma-separated from this fixed vocabulary: Communication, Auth-Session, Data-Storage, File-IO, Cryptography, Third-Party-SDK, Config-Secrets, Logging-Telemetry, Payment-IAP, Anti-Cheat-Integrity, Admin-Backoffice, Build-Deploy), entry_points, data_handled (plain language, flag anything that looks like player PII explicitly), trust (Fully-Untrusted / Semi-Trusted / Trusted), trust_boundary_crossed (yes/no + which boundary), external_deps, path.

Prompt 1B — Third-party binary & phone-home triage (vendor-trust workstream)

Run once, whole codebase — supply-chain specific
You are triaging supply-chain and vendor-trust risk in a codebase delivered by a third-party vendor, separate from the standard ASVS-style code review.

ATTACHED EVIDENCE
- List of all non-source binary artifacts shipped in the repo (native plugins, .so/.dll/.dylib, prebuilt libraries, asset bundles with embedded code).
- `strings` + entropy-scan output for each binary (candidate embedded keys/certs/high-entropy blobs).
- Regex pass results for outbound domain/IP literals found anywhere in source or binaries.
- SBOM with license field populated per dependency.
- Full list of third-party SDKs integrated in the client (ad networks, analytics, crash reporting, push, IAP).

TASK
1. For each opaque binary: state what evidence exists about its purpose (filename, adjacent code that calls into it, any embedded strings that reveal function), and mark it Unauditable-As-Is if there is no source available. Recommend whether it should be sandboxed/dynamically analyzed, or treated as fully untrusted at the interface level (i.e., validate everything crossing into/out of it as if from an external attacker).
2. For each outbound domain/IP literal found: classify as (a) known first-party infrastructure, (b) known third-party SDK endpoint (name the SDK), or (c) unrecognized — flag unrecognized ones as highest priority for manual verification, since these are the candidates for undisclosed telemetry or update channels.
3. For each embedded high-entropy string: state whether it looks like a cryptographic key/cert/token, and if so, whether it appears to be a static secret shared across all installs (bad) vs. a public key/cert (expected).
4. Review the SBOM license column for anything copyleft (GPL/AGPL family) or with a missing/unrecognized license — flag for legal review given this is vendor-delivered IP being integrated into a commercial product.
5. Separately list any dependency or embedded routine that looks like a non-standard/substituted cryptographic primitive (e.g. SM2/SM3/SM4 or other algorithms outside the project's stated crypto standard) — flag for legal/compliance review rather than treating as a plain code finding; this can indicate the vendor building to a different regulatory baseline than yours.
6. Flag any self-update or remote-config mechanism that can change executable behavior post-install without going through your release process — this is the highest-severity supply-chain risk category and should be called out even if implemented "correctly," because the trust question is who controls the update channel, not whether the channel is secure.

OUTPUT FORMAT
One table per task (1-6), each row citing the specific file/binary/evidence line it's based on. End with a short "escalate to legal" list pulling together anything from steps 4-5.

Prompt 2D — Player-data lineage (PII / GDPR / PIPL / COPPA)

Run once per data tag, e.g. device_id, precise_geo, email, payment_token
Trace one specific category of player data end-to-end through the system, for a data-protection review.

DATA TAG UNDER REVIEW: {{DATA_TAG}} (e.g. "device ID", "precise geolocation", "email address", "IAP payment token")

ATTACHED EVIDENCE
- Every inventory row from Phase 1 where data_handled includes this tag.
- The cross-environment dataflow diagram from Prompt 2C.
- Any existing privacy policy or consent-flow description you have for this data type.

TASK
1. Identify the collection point(s): where does this data first enter the system, and is it collected with an observable consent/permission step, or silently?
2. Trace every hop this data takes: client → transmission → server-side processing → storage (which datastore, encrypted at rest or not) → any third-party sharing (name the recipient SDK/service if it's shared with an ad network, analytics provider, etc.) → retention period if stated anywhere, → deletion/export mechanism if one exists.
3. Identify every point where this data crosses a jurisdictional boundary (leaves the player's region, enters vendor-operated or China-based infrastructure, is shared with a third party in a different jurisdiction).
4. 5. Rate the gap between what the code/infra evidence shows and what the regulation requires as Compliant / Partial / Non-Compliant / Unknown — Unknown means the evidence doesn't show a control either way, which is itself worth reporting distinctly from "confirmed non-compliant."

OUTPUT FORMAT

```mermaid

```

Map the Phase 1 inventory into OWASP ASVS chapters (v5.0 as of this writing — confirm you're standardizing on the same version before you start, since numbering shifted from 4.0.3). Mapping is many-to-many: one component can land in several chapters.

Prompt 3A — ASVS mapping

Run once per location, or once for the whole inventory if it fits context
Map a component inventory to OWASP ASVS chapters for a targeted, evidence-driven review (as opposed to running the entire ASVS checklist against everything, which wastes review time on chapters that don't apply to a given component).

ASVS-driven assessment

The deep-review phase: one prompt template, run per ASVS chapter × component group from the Phase 3 worklist, plus two supplements for what ASVS doesn't cover.

Prompt 4A — ASVS chapter assessment

Run per (ASVS chapter, component group) pair from the Phase 3 worklist
You are performing a targeted ASVS-based code review. Assess the listed components against ONE ASVS chapter only — do not drift into other chapters even if you notice unrelated issues; note those separately at the end instead.

ASVS CHAPTER: {{ASVS_CHAPTER}} (e.g. "V6 Authentication" — cite the exact requirement numbers you're checking against, per {{ASVS_VERSION}})

Prompt 4B — Native memory-safety supplement (C++ game server)

Run per C++ component — ASVS doesn't cover this well
Review a C++ component for memory-safety and native-code risk classes that ASVS does not operationalize, using CWE and SEI CERT C++ as the reference standards.

COMPONENT: {{COMPONENT_ID}}
ATTACHED EVIDENCE
- Source for this component, especially anything parsing untrusted network input.
- cppcheck / clang-tidy / Clang Static Analyzer output already scoped to this component.

TASK
Check specifically for, citing file:line for any instance found:
1. Buffer overflows / out-of-bounds access in packet or file parsing (CWE-119 family).
2. Use-after-free and double-free (CWE-416, CWE-415), especially in connection/session teardown paths.
3. Integer overflow/underflow feeding into allocation sizes or loop bounds (CWE-190/191).
4. Race conditions on shared game state accessed from multiple threads without synchronization (CWE-362).
5. Unchecked return values from allocation or I/O calls that lead to null-deref or silent failure (CWE-252).
6. Format-string and unsanitized-input-to-format-function issues if any C-style formatting is used (CWE-134).
7. Deserialization of untrusted network input without bounds/schema validation before use.

For each finding, use the same canonical YAML-frontmatter schema as Prompt 4A, with `asvs: N/A - see supplement: native-memory-safety` and the appropriate CWE. Rate severity by whether the flaw is reachable from untrusted client input (game server accepts direct client connections, so most parsing code qualifies) — reachable memory-safety bugs in a network-facing C++ service are presumptively High or Critical.

OUTPUT FORMAT
Finding blocks only, ordered by severity, plus a one-line note on any of the 7 categories where you found nothing to report.

Prompt 4C — Game trust & economy integrity supplement

Run against client + game server + backend components tagged Anti-Cheat-Integrity or Payment-IAP
Review the listed components for game-specific trust and economy-integrity risks that neither ASVS nor generic memory-safety review covers.

COMPONENTS: {{COMPONENT_LIST}}
ATTACHED EVIDENCE: source excerpts for authoritative-state handling, IAP validation, and any anti-cheat/integrity checks.

CHECK FOR, citing file:line:
1. Client-authoritative state: does the client ever send a value the server trusts without independent verification (score, currency balance, position/speed for movement validation, inventory contents)? Any client-authoritative economy value is a presumptive finding.
2. IAP/receipt validation: is purchase validation done server-side against the platform's (Apple/Google) receipt-verification API, or does the client merely assert "purchase succeeded"?
3. Save-state and asset-bundle integrity: are local save files or downloadable asset bundles signed/verified before use, or can a modified client load arbitrary tampered content?
4. Matchmaking/session abuse: can a client join a match, request state, or claim rewards without a corresponding valid game session on the server?
5. Rate limiting on economy-affecting actions (trades, rewards claims, currency purchases) — absence of rate limiting here is a fraud/abuse finding, not just an availability one.

Use the same canonical finding schema as Prompt 4A, with `asvs: N/A - see supplement: game-trust-integrity`.

OUTPUT FORMAT
Finding blocks ordered by severity (client-authoritative economy state and unvalidated IAP receipts are typically Critical/High), plus a short note on anything checked with no finding.
05

CVE verification & reachability

Turn a raw SBOM/CVE dump into a small, defensible list by triaging reachability rather than reporting every hit.

Prompt 5A — Reachability triage

Batch by dependency — group CVEs per package, not one prompt per CVE
Triage dependency CVEs by reachability, using the codebase's actual usage of the affected package rather than treating "package is present" as equivalent to "vulnerability applies."

ATTACHED EVIDENCE
- osv-scanner (or equivalent) results for package {{PACKAGE_NAME}} version {{VERSION}}, including the CVE list, affected function/module per advisory, and fixed version.
- Every call site in the codebase that imports or calls into this package (grep/call-graph results — attach, don't ask the model to search from memory).

TASK
For each CVE against this package:
1. State the vulnerable function/module per the advisory.
2. Check the attached call sites: is the vulnerable function/module actually invoked anywhere in this codebase, directly or transitively through another function you can see is called?
3. Classify as: Confirmed-Reachable (vulnerable code path is called, and at least one caller passes data that could plausibly be attacker-influenced — trace it back toward the nearest trust-boundary-crossing input if you can), Present-Unreachable (package used, vulnerable path not called), or Present-Unused (package imported but nothing in the codebase references it — candidate for removal regardless of the CVE).
4. For Confirmed-Reachable results only, produce a finding using the canonical schema from Phase 4A, with the `cve` field populated and severity taken from the advisory's CVSS score, adjusted down one tier if reaching the vulnerable path requires privileged/authenticated access rather than being reachable pre-auth.
5. For Present-Unreachable and Present-Unused, output one summary line each (package, CVE, classification, one-line reason) — these still belong in the report as a hygiene/upgrade backlog, just not as security findings requiring urgent remediation.

OUTPUT FORMAT
Finding blocks for Confirmed-Reachable only, then a compact table for everything else: Package | CVE | Fixed Version | Classification | Reason.
This is the phase most worth spending human review time on — reachability judgment calls are exactly where an LLM triage can be wrong in either direction. Spot-check a sample of Present-Unreachable classifications by hand before trusting the whole batch, especially for anything the advisory rates Critical.
06

Consolidation & dedup

Findings arrive from Phases 4 and 5 across many separate LLM runs — the same root cause often surfaces from more than one angle. Consolidate before publishing.

Prompt 6A — Consolidation pass

Run once, all raw finding blocks attached
Consolidate raw findings collected across multiple review passes into a single deduplicated set.

ATTACHED EVIDENCE: every finding block produced in Phases 4 and 5 (concatenated, YAML-frontmatter format as specified earlier).

TASK
1. Identify findings that describe the same underlying root cause reached from different angles (e.g. an ASVS chapter finding and a memory-safety supplement finding both citing the same unvalidated-input function) — merge these into one finding, keep the most complete evidence/remediation text, and list the merged IDs in a `merged_from:` field added to the frontmatter.
2. Identify findings whose `location` is identical or overlapping but whose `severity`/`confidence` disagree — do not silently pick one; surface the disagreement and recommend the more conservative (higher) severity pending human review, noting both original ratings in the description.
3. Renumber the final `id` sequence to be contiguous per component prefix, and produce a change log mapping any renumbered ID back to its original.
4. Produce a summary table: total findings by severity, by location, by ASVS chapter/supplement, and by regulatory tag (GDPR/PIPL/CCPA/COPPA) — this becomes the executive-summary input in Phase 8.

OUTPUT FORMAT
The full deduplicated set of finding blocks (canonical schema, unchanged structure), followed by the ID change log, followed by the summary table.
07

Markdown → SARIF

Deterministic step, not an LLM step. The consolidated markdown (YAML-frontmatter findings) is parsed by a small Python script into SARIF 2.1.0 for ingestion into CI, code-scanning dashboards, or ticketing.

Why frontmatter, not prose parsing

Every finding schema field (severity, cwe, asvs, location, cve) is structured in YAML frontmatter. The current run-owned converter is appsec-review-process/critical_findings_sarif.py and is invoked through Dagster, not from this archived playbook.

SARIF level mapping:
  Critical, High → "error"
  Medium         → "warning"
  Low, Info      → "note"

Per finding block:
  rule.id           = cwe (fallback: category)
  rule.name         = title
  result.ruleId     = rule.id
  result.message    = description body
  result.level      = mapped from severity
  result.locations  = parsed "path:line" → SARIF artifactLocation + region
  result.properties = { asvs, data_classes, regulatory, cve, confidence, status }

One SARIF run per component `location` (Client / Game Server / Backend / Cloud-Infra),
or a single run for the whole set — either works; per-location runs make it easier to
gate CI on one component at a time.

Reporting & retest

Prompt 8A — Executive summary

Run once, consolidated findings + summary table attached
Write a one-page executive summary of this security review for a non-technical stakeholder audience (studio leadership, not engineers).

ATTACHED: consolidated finding set + summary table from Phase 6, the four zone threat models, the cross-environment dataflow diagram.

TASK
1. Open with the single highest-severity, highest-confidence finding in plain language — what could happen, to whom, not the technical mechanism.
2. State the overall risk posture in one paragraph: how many Critical/High findings, concentrated in which zone, and whether the pattern suggests a systemic issue (e.g. "most High findings are client-authoritative trust issues, one root cause across many symptoms") versus scattered unrelated bugs.
3. Call out the PHP 5 end-of-life status and the vendor supply-chain findings as their own named risk items, even if no individual CVE, ranked by business impact rather than folded into the general count — these are the two categories most likely to be underweighted if only counted as "one finding each."
4. Summarize the regulatory exposure from Phase 2D findings (GDPR/PIPL/CCPA/COPPA gaps) as a distinct short section — this typically needs different stakeholders (legal/privacy) than the rest of the report.
5. Close with a prioritized remediation order (not just a severity-sorted list — sequence by what unblocks what, e.g. "fix the client-authoritative economy issue before anything else in the anti-cheat category becomes meaningful").

OUTPUT FORMAT
Markdown, no more than one page rendered, no code excerpts — this document links to the full findings set rather than repeating it.

Prompt 8B — Retest verification

Run per finding marked "fixed" by the team
Verify whether a specific finding has actually been remediated, using a diff rather than trusting the "fixed" label.

FINDING: paste the full finding block being retested.
ATTACHED: diff of the change claimed to fix it (before/after source), plus updated SAST output for this file if available.

TASK
1. Confirm the specific line(s) cited in the original finding's `location` were actually changed — if the diff doesn't touch that location, this is not a fix, regardless of what else changed.
2. Check whether the fix addresses the root cause described in the finding's Impact/Description, or only a narrower symptom (e.g. validates one field but the same unvalidated-input pattern exists two lines later, or a client-side check was added without an equivalent server-side one).
3. Check for regression risk: does the fix change behavior in a way that could break a legitimate use case, based on what you can see in the diff?
4. Recommend a new `status`: Fixed (root cause addressed, verified in diff), Partially-Fixed (narrower than the finding, restate what's still open as a new finding with `merged_from` pointing at the original ID), or Not-Fixed (diff doesn't address the location/cause — keep status Open and say why).

OUTPUT FORMAT
One paragraph verdict + the recommended `status` value +, if Partially-Fixed, a new finding block for the remaining gap.
