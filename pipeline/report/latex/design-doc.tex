% ================= page 1: the message =================
\begin{bluf}
Every security review should run the same way, whoever starts it and whatever the target. v3 turns
the review into a pipeline: one command takes a repository from checkout to a scored report, with
no one running tools by hand along the way. Each step uses pinned tools and fixed rules, every
finding has to survive an attempt to disprove it, and anything the pipeline could not examine is
listed in the report instead of being passed over. People review the finished report; they do not
operate the review.
\end{bluf}

\metrics[4]{%
\metric{1}{Command to run}{Checkout to report, unattended}%
\metric{4/4}{Seeded defects found}{Notepad++ 8.5.6; stock CodeQL found 0/4}%
\metric{0}{False findings shipped}{EASTL baseline: 8 custom-pack hits, none real}%
\metric{13}{Pinned tool images}{Same versions every run, no network at scan time}}

\subsection*{What this means for the organization}
\begin{itemize}
\item \textbf{Repeatable.} The same target at the same commit produces the same evidence and the same
  report. Results hold up when a vendor disputes them.
\item \textbf{Hands-off.} Build, scanning, analysis, refutation, verification and scoring run as one
  flow. Reviewer time goes to judging the report, not running tools.
\item \textbf{Honest about coverage.} A step that did not run is reported as a gap. The report can
  only call a target clean when enough of the review actually happened.
\item \textbf{Not tied to one person.} The process lives in the pipeline, so reviews do not stop when
  a particular reviewer is unavailable.
\end{itemize}

\section{How the process runs}
A review is a fixed sequence of jobs started by one command. Nothing in the sequence waits for a
person. The evidence side gathers facts and never makes a claim; the review side never promotes a
tool hit to a finding without trying to refute it and verifying what survives.

\subsection*{What makes it repeatable}
\begin{enumerate}
\item \textbf{Pinned everything.} Tool versions, container images and reference data are fixed per
  run; nothing is looked up live while scanning.
\item \textbf{Fixed contracts.} Every job has declared inputs, outputs and a pass/fail check. A job
  that fails stops with a recorded reason and can be resumed from that point.
\item \textbf{Evidence-first.} Every finding cites a file and line or a tool output, so anyone can
  trace it back.
\item \textbf{Target content is data.} Nothing in the code under review can steer the process.
\end{enumerate}

\section{Technical detail}
\subsection{Scoring}
Each finding's priority starts from its CVSS 4.0 base score and is scaled by how strong the
evidence is, whether it survived verification, whether the code is reachable, and exploitation
signals:
\[ P_f = \min\!\big(10,\; S_f \cdot e_f \cdot v_f \cdot r_f \cdot t_f\big) \]
The overall rating is the band of the highest non-refuted priority. A Low or clean rating is only
issued when process assurance, the share of the review that actually ran, is at least 0.85;
otherwise the rating is \emph{Indeterminate}.
