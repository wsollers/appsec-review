# Job catalog, information flow, interchange JSON and raw-tool-output audit (2026-11-07)

Scope: repository revision `42dee4d`, read-only review of `src/appsec_review/` against `docs/`,
`README.md`, `AGENTS.md`, `deploy/dagster/README.md` and `appsec-review.toml`. Every claim names the
file (and symbol or line) it was checked against. Nothing here was verified by running a review;
"not verified" marks anything that would need a live run. Unimplemented formal-verification jobs
(`docs/formal-verification/buildout-plan.md`) are excluded from the inventory and discussed only
in sections 3 and 4.

## Summary

1. 46 jobs are registered (`runtime/registry.py:99-164`) and all 46 have TOML tables, `datasets.py` and `job.py`; 44 are in `wave1_review`, two are outside it (`job_third_party_data_sync`, `job_build_iteration`), and two ship disabled (`job_cpg_analysis`, `job_svf_alias_analysis`; `appsec-review.toml`).
2. Every job has an operations or architecture page and the job table in `docs/architecture/jobs-and-runtime.md` is complete and current; the per-dataset table in `docs/architecture/dossier-data-inventory.md` is stale (145/44 claimed vs 153 declarations across 46 modules, two jobs and five output kinds missing, one renamed kind).
3. Per-file documentation is weak for the cluster-producing jobs: the per-case tree under `data/cpp/projects/<case>/` (10 file kinds), the per-scope CodeQL tree (`database-checkpoint.json`, `query-checkpoint.json`, `queries/<profile>/sarif/results.sarif`, `protected-replay.json`), per-scope clang/clangd/SVF `checkpoint.json`/`seeded-ledger.json`, and the inference-review attempt tree are undocumented as clusters (key, ordering, bounds).
4. The `wave1_review` graph in `topology.py` is faithfully reproduced in `deploy/dagster/README.md` except for `job_openvex_export`; the CLI order in `docs/operations/wave1-review.md` omits `openvex_export`; the Mermaid flow in `docs/architecture/evidence-sources-and-dataflow-retrieval.md` has 7 edge errors and omits 9 jobs; `review-process.html` labels PoC/remediation "default off / planned" although both ship enabled.
5. `indexing/input_matrix.py` and its doc table agree row-for-row (63 rows); the only text drifts are that the doc lists `graph` as a query set for five rows (code lists none) and the OWASP `UPSTREAM_JOBS` allowlist still names unregistered `job_target_documents` (`owasp_workbench/evidence.py:19`).
6. The envelope layer (`claim.json`, task `status.json`, `outcomes.json`, `handoff.json`, `latest.json`, dataset contract) is one shape for every job and is byte-verified; the payload layer (`result.json` outputs, per-job summaries, gaps, dispositions) is not: 18 schema names carry two or more live versions, gaps are free strings in 24+ jobs while `ProducerGap` is used by none, and only 6 of 46 jobs validate against a JSON Schema in `docs/schemas/`.
7. `status.json` (attempt and task) carries no `schema` field; task receipts are only `unit-execution/2` by convention (`runtime/units.py:146`, `runner.py:621`).
8. Raw tool output is already kept protected and normalized at the producer for SAST/CodeQL/artifact scanners; the exceptions that re-parse a sibling's raw bytes are Grype (Syft JSON), `job_code_graph_index` (CodeQL export JSON rows), `job_post_build_security_assessment` (raw `compile_commands.json`, `link.txt`), the clangd/clang/CPG/SVF consumers (materialized case roots), and prioritization/change-context (Tree-sitter JSONL via shards is fine, but the accepted-handoff reader is reimplemented 20+ times).
9. Recommendation: keep SQLite shards and the shared `{path, sha256, size_bytes}` reference as the neutral form; do not introduce CSV; add a typed `appsec-review/typed-rows/1` JSON Lines contract for the three places that must hand bulk rows between jobs before shard build (CodeQL export, Tree-sitter nodes, SVF/Clang CFG); move Grype and post-build onto typed inputs.
10. Top priorities: fix the stale catalog/diagram pages (S), add a per-job "files written" appendix generated from `datasets.py` (M), adopt `ProducerGap` and a shared `accepted_handoff()` reader (M), version-pin the per-job `result.json` output records with closed schemas (L).

### 1.4 Narrative

The declaration layer is strong: `runtime/datasets.py` forces every job to claim every run-owned file it writes, and `indexing/inventory.py:651-653` turns an unclaimed file into an audit violation (`unaccounted_file`). That means the authoritative "what does this job write" list already exists in code, but it is expressed as glob patterns with a one-line description, and the docs restate it inconsistently: the dossier inventory copies it (now stale), the operations pages describe behaviour rather than files, and nothing describes clusters. The three jobs whose output is a tree of per-scope artifacts consumed by other jobs (`job_cpp_compiled_analysis` → clangd/clang/SVF/CPG/post-build; `job_codeql_analysis` → `job_code_graph_index`; `job_tree_sitter_ast` → prioritization/change-context/code graph) are exactly the ones with the thinnest file-level documentation.

Consumption declarations (`CONSUMES`) are also uneven: `job_security_tagging` declares nothing, `job_owasp_control_assessment` declares 19 including a nonexistent job, and `topology.py` edges are a different (narrower) set again. The runtime does not cross-check `CONSUMES` against `wave1_dependencies` (checked: `runtime/dependencies.py:26-28` uses `consumes` only for the generic planner; topology hardcodes its own edges).

## 3 Interchange JSON

### 3.1 What is uniform (verified)

### 3.3 Proposed standard interchange envelope

Keep `job-handoff/2` unchanged (it already is the envelope). Standardise the layer beneath it, which is where the drift is. Proposed `appsec-review/job-record/1` conventions:

| Field | Required | Rule |
|---|---|---|
| `schema` | yes, every JSON document | `appsec-review/<kebab-name>/<int>`; one segment, lowercase kebab, integer version; no underscores, no nested paths. Deprecate the five nonconforming ids by issuing `/N+1` under a conforming name. |
| `run_id`, `job_id`, `attempt_id`, `unit_id` | yes on every attempt-owned record (`result.json`, task `status.json`, per-job summary, per-scope checkpoint) | copied verbatim from `claim.json`; `unit_id` is `<step>.<task>`. ### 3.4 Migration path (immutability-preserving)

1. Add the enums/records to `interchange.py` and the JSON Schemas; no behaviour change.
2. Add `schema` to new `status.json` files and a `task-receipt/1` entry to the runtime claims; readers accept schema-less receipts from existing runs (`verify_outcomes` already reconstructs from bytes, so old attempts stay verifiable).
3. Per job, convert `gaps` to `ProducerGap` and `terminal_status` to the enum, bumping that job's `schema_identity` (`Job.schema_identity`) so resume planning reruns it (`resume.py:110-116` compares `schema_identity`); accepted attempts of older runs are untouched and remain `handoff/2`-valid because the runtime already wraps string gaps.
4. Collapse the per-job `_accepted_handoff` copies onto one `appsec_review.runtime.consume.accepted_handoff(context, job_id)` that resolves by `context.upstream_handoffs[job_id]` digest (reuse `retrieval/core.py:128`), and make `Job.consumes` the only allowed argument set.
5. Make `CONSUMES` and `wave1_dependencies` agree by a unit test (every edge in `topology.py` must appear in the consumer's `CONSUMES`, and vice versa for propagating producers); fix `job_security_tagging` (`()`) and `job_owasp_control_assessment` (`job_target_documents`).
6. Retire duplicate schema versions one reader at a time (`review-package/3` vs `/6`, `unit-execution/1` vs `/2`) by deleting the older writer, never the older reader until no run under retention uses it.

### 4.2 Analysis

The repository already follows "normalize at the producer, keep raw bytes protected" for the scanner classes (SAST, CodeQL SARIF, artifact scanners, CI, Clang, SVF, clangd, Tree-sitter, debug symbols): raw output is a `protected` dataset, parser-input bytes are content-addressed (`provenance.retain_native_output`), and consumers query SQLite shards through `IndexBuilder`/`load_verified_manifest`. The dataset audit enforces that nothing indexable is left unclassified. The residual raw-passing cases are:

1. **CodeQL graph export → `job_code_graph_index`.** The export is a typed JSON table (`{schema, query_id, columns, rows[[...]], row_count, truncated, bqrs_sha256}`, `graph/contract.py:381-392`) with its own manifest and bounds, not a native tool format. It is already the "neutral tabular" form; the only question is where normalization into `graph` facts lives. Keeping it in the consumer is defensible because the producer's contract is "exact BQRS decode" and the consumer owns cross-checks.
2. **Grype ← Syft raw JSON.** Tool-native dependency, inside one job; Grype's own input contract requires Syft JSON. Acceptable as a tool chain, but the mount should be of a content-addressed object with its retention receipt, not of `scratch/output.json`.
3. **`job_post_build_security_assessment` ← raw `compile_commands.json` / `link.txt`.** This is the one true violation: a second job re-parses a build tool's raw file from another job's protected case root, with its own bounds (16 MiB / 4096 rows) and its own argv-shaping (`_argv`), duplicating what `job_cpp_compiled_analysis` already normalized into `normalized-compile-commands.json` / `normalized-link-commands.json` and the `cpp-*-compiled` shard.
4. **Index consumers ← materialized case root.** clangd/clang/CPG/SVF mount `data/cpp/projects/<case>/source` read-only and receive compile rows through the handoff; they re-verify every file hash (`cpp_index_scopes.py:170-190`). This is source custody, not raw-tool-output passing; it is correct.

Format choice:

- **CSV/TSV**: no schema, no typing (every cell is text), quoting rules differ per writer, no nested values (locations, references, gaps are nested), and no deterministic byte identity without a canonicalisation rule. The repository's own CSV uses are inputs to tools (`scope.csv`, `seeds.csv`, header-less external predicates for QL) and Joern's export reader, both bounded and never a job boundary. Rejected for interchange.
- **JSON Lines**: one canonical JSON object per line (sorted keys, compact separators, `ensure_ascii=False`, `allow_nan=False`, as `normalize.py:136` and `interchange._canonical` already do) gives deterministic bytes, hashability, streamability, bounded per-record validation and nested values. It lacks typed columns and random access; it is right for producer→shard-builder bulk rows and for append-only ledgers (`claim-ledger.jsonl`).
- **Parquet**: typed columns, compression and column pruning, but it adds a binary dependency (pyarrow), byte determinism depends on writer version/encoding choices (would have to be pinned in `tool_identity` and the shard fingerprint), and the retrieval layer has no reader for it. Not justified at current volumes (bounded shards, 128-char shard ids, row limits in the 10^5 range).
- **SQLite shards are already the neutral form** for everything a reviewer or another job queries: `entities(identity, kind, native_id, name, text, payload_json)`, `locations`, `relations`, `coverage`, `metadata`, `search_fts` (`retrieval/index.py:236-260`), deterministic byte identity (sorted inserts, fixed pragmas, fsync-then-hash), immutable publication, manifest pinning and a shared `EntityKind`/`RelationKind` vocabulary. The gap is not the storage form; it is that the *row payload* (`payload_json`) is schema-free per producer (`sanitize_producer_data` redacts but does not validate) and that there is no typed row contract for the pre-shard bulk handoff.

Information loss: normalization is lossy by design (bounded selections, redaction), and the repository mitigates it with `NativeResultReference` selectors back into retained bytes. That mechanism exists for scanner observations only (`provenance.py`; used by evidence collection, CodeQL, artifact security per `docs/architecture/job-interchange.md:165-167`); Clang/IR/SVF/Tree-sitter rows have `producer_location`/`native_id` but no selector into the protected file, so replay from a row to the raw byte range is not uniform.

### 4.3 Recommendation

Rule: **"A producer publishes typed rows; raw tool output is protected, content-addressed provenance; no job parses another job's raw tool output or protected workspace file."** Concretely:

1. Raw bytes a tool wrote are retained once, as a protected dataset *and* as a `data/shared/objects/<sha256>` object with a `native-output-retention/1` receipt (extend `retain_native_output` beyond scanners to AST/IR/CFG/SVF/clangd/CPG/Tree-sitter outputs).
2. The producer emits typed rows under a closed per-family schema (`appsec-review/<family>-row/N`) into (a) the SQLite shard, for anything queried, and (b) a canonical JSON Lines file `rows.jsonl` with a sidecar `rows.json` `{schema, row_schema, row_count, truncated, sha256, bounds}` when another job needs bulk rows before indexing (CodeQL export, Tree-sitter nodes, SVF/CFG facts). Every row carries `scope_id`, `target_snapshot`, a `SourceLocation` when resolvable and a `native_ref` `NativeResultReference` selector into the retained raw object.
3. A consumer reads only: accepted shards through `load_verified_manifest`, `rows.jsonl` files bound in the producer's handoff `artifacts`, or `{path, sha256, size_bytes}`-referenced JSON documents with a declared schema. Reading `scratch/`, `work/`, `build/`, `analysis/` or any `protected` pattern of another job is forbidden by a test that resolves each consumer's opened paths against the producers' dataset declarations (the inventory already classifies every file, so the test is a static allowlist check).
4. No CSV at any job boundary; Parquet deferred until a shard exceeds the SQLite builder's practical limits (none do today).
