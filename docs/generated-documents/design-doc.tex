\begin{bluf}
appsec-review is an automated application security engineer: a pinned, repeatable process that does
the routine, evidence-heavy work of an AppSec review (scope, build, scan, threat-model, read code, argue
and verify each finding, score, write up) across more code and more targets than one person can. It is
\emph{almost} an engineer, never a replacement. People keep the judgement that carries accountability:
what the risk means to the business, what to accept, and whether the report goes out. Every lane is
built and unit tested; no target has yet run through to a report.
\end{bluf}

\subsection*{What leadership should know}
\begin{itemize}
\item \textbf{It does the routine work, not the accountability.} Machines gather, build, scan,
read and argue; a named person accepts risk and signs the final package.
\item \textbf{A tool hit is never a finding.} A finding has passed red-team, blue-team and
independent verification, and every claim cites evidence that resolves to exact bytes.
\item \textbf{Silence is never ``clean''.} A scanner that did not run or a build that failed is a
coverage gap in the report, never ``no issues found''.
\item \textbf{Python keeps the books; the model supplies judgement only} (ADR-0013). Ids, hashes,
citations, scores and reachability are computed, never taken from the model.
\item \textbf{It is not yet proven end to end.} Ten jobs are qualified; all four targets have run
part of the flow and 108 breakages are logged, but none has produced its report yet.
\end{itemize}

\subsection*{What changes for the organisation}
\begin{itemize}
\item AppSec engineers review verified findings, gaps and attack paths instead of building targets
and triaging raw scanner output.
\item Every review yields the same package (findings, coverage, gaps, provenance), so reviews compare
across teams and over time. Depth is a setting (\mono{probe}, \mono{standard}, \mono{full}), not
a staffing decision.
\item New standing duties: persona ownership, reference-feed upkeep and sign-off of each final package.
\end{itemize}

\section{What the process is, and where the line is}
An application security engineer spends most of a review on work that follows a method: find out what
the system is, get it to build, run the tools, read what they say, model the threats, read the risky
code, check each suspicion against the evidence, rate it and write it down. appsec-review encodes that
method as a graph of 81 lifecycle jobs run by Dagster. Each job gets bounded input and publishes an
immutable attempt with status, coverage, permissions and lineage. Downstream jobs re-check hashes
rather than trusting copied prose.

The process reviews an authorized snapshot: source, build metadata, binaries, images, IaC,
dependencies, configuration and documents. It may compile the target to recover compiler semantics.
Build scripts are treated as hostile and run in a disposable, no-network, least-privilege container.
It does not probe production, call live cloud APIs, run authenticated DAST, exercise network services
or attempt live exploitation.

The line between the process and the engineer is set by what can be checked. Where a conclusion can be
derived from evidence (does this path exist, does this call reach that sink, what CVSS score follows
from these metrics), Python derives it. Where it needs judgement about code (is this a plausible
attack, does this mitigation hold), a model persona gives an opinion and Python validates the form
and the citations. Where it needs accountability (is this risk acceptable to the business, may this
report be published), a person decides. Section~\ref{sec:people} lists those decisions.

Independent evidence families run at the same time and meet at explicit rendezvous points. A
rendezvous waits for every expected member and classifies each one (succeeded, failed, blocked,
timed out, missing). A deterministic merge checks identities, contracts and citations and keeps
dissent. Evidence-qualified quorum applies evidence and independence thresholds, not a headcount.
Roles talk through typed, hash-bound artifacts and an append-only claim ledger, never a shared chat.
The component map is the shared scope key: it routes components to language tools, threat work,
standards, native analysis and hunters.

\section{Why it scales}
A person reviews one component at a time. The process splits the same work along the lines the
target already has and runs the pieces in parallel under fixed limits.
\begin{itemize}
\item \textbf{Parallel by component and language.} The eight per-language CodeQL nodes run side by
side; a compiled language without a successful build is a gap, not a failure (ADR-0023). Native
analysis runs per compile invocation and build unit, so one failure is one gap (ADR-0014).
\item \textbf{Sharded reviewer pools.} Each review stage splits its claims across reviewer instances
(default 3, three calls at once), each reviewing a different shard as a different persona. Each
claim is reviewed once per stage (ADR-0021). Hunters shard the code by component into three groups,
components with the most P1/P2 leads first (ADR-0018). Workbench cells run one, two or three at once
by budget class.
\item \textbf{Persona pools.} 75 persona and 48 role records sit in
\mono{appsec-review-process/personas/}. Attackers, defenders, verifiers and scorers come from
separate lists, so the persona that argues a claim is never the one that verifies it.
\item \textbf{Budget tiers.} \mono{probe}, \mono{standard} and \mono{full} set each model call's
limits: 200k, 800k and 1.6M input tokens; 15, 30 and 60 minutes. A standard call is capped at
2~USD; the default hunter pool therefore spends at most about 6~USD. Tiers change depth, never the
evidence or permission rules.
\item \textbf{Shared, bounded capacity.} Dagster pools cap concurrent work across all runs (five
model slots, two container slots). Three targets ran at once on one host on 2026-09-27/28.
\item \textbf{Reusable pinned tools.} Tools live in local images pinned by digest and recorded
before use. The same image serves every target; workers never pull opportunistically.
\item \textbf{Offline reference feeds.} NVD and OSV are synchronised outside the review into
immutable snapshots, and Grype databases are registered the same way. A 14-day ceiling
(1,209,600~s) applies; a missing or stale snapshot is a gap or a block, never a silent pass. The
OSV index measured on 2026-09-29 (seven package ecosystems; Debian and Alpine were added on
2026-10-03 for base-image packages and are not yet measured) holds 283,781 advisory records, builds in about 12~s at 195~MB,
and answers lookups in under 1~ms against about 6~s from the raw archives. MITRE ATT\&CK, CAPEC
and the full CWE catalog will use the same feed rules when brief~O merges (decision log D-05, D-11).
\item \textbf{Index-first lookup.} Models query pinned inputs through read-only lookup tools instead
of having whole files pasted into the prompt. On freeciv21, a 6,100-file inventory is summarised by
folder, about 6K characters instead of 895K.
\item \textbf{Result caches.} Accepted attempts are reused on relaunch: a pure-reuse relaunch of
hello-autotools ran 46 steps in 2.4 minutes (2026-09-28). A persona result cache answers an
identical model request without a new call. Re-execution after a fingerprint change is still
expensive: 41 minutes to re-plan 53 units on appsec-multi-vuln. The tool-output cache and per-item
memo are open (brief~N).
\item \textbf{Dev-mode restart} (ADR-0025). In development, a job ported to the generic item
executor reruns only when the content or shape of its inputs changed; one job is ported so far. Dev
results are never evidence. Not yet run live.
\end{itemize}
Throughput per host and reviews per engineer-month are \tbd{measure on the four targets}.

\section{Why it can be trusted}
\begin{itemize}
\item \textbf{Evidence first.} A tool hit, a STRIDE hypothesis or a hunter's idea is a candidate. It
becomes a finding only after independent verification, and every claim cites a producer, an
artifact hash and a line range that consumers re-read and re-hash.
\item \textbf{The pipeline gathers; it does not judge.} Deterministic jobs collect and normalise
evidence. Conclusions are carried only by enumerated values checked against each job's allowed claim
classes, never parsed from prose (ADR-0013).
\item \textbf{Python derives every mechanical field.} Ids, hashes, lineage, citations, CVSS scores,
reachability verdicts and chain states are computed, not accepted from the model. A model reply that
cites a location Python cannot resolve becomes a gap.
\item \textbf{Gaps stay visible.} A tool that did not run, a build that failed or an unsupported
language is a coverage gap in the report, never ``no issues''. \mono{OK\_WITH\_GAPS} is an honest
result, not a failure.
\item \textbf{Separate roles.} Red team proposes, blue team refutes, an independent verifier decides,
and a scorer rates. Each runs under its own registry role, which limits the claim class it may emit
(ADR-0024). The blue team cannot verify; nobody promotes their own proposal.
\item \textbf{Severity is earned.} Critical needs a reachability witness path; without one the cap is
High. The CVSS 4.0 table was checked against FIRST's calculator on 204,976 vectors with no mismatch
(2026-09-29).
\item \textbf{Target content is data.} Source, documents, logs and search hits under review cannot
direct the process or grant permissions.
\item \textbf{Pinned and reproducible.} Tools, images, reference snapshots and prompts are pinned and
hashed; each job's fingerprint covers its own code and inputs. Scans run offline.
\item \textbf{Dev runs are never evidence.} A dev-mode receipt carries \mono{evidence\_grade: false};
production never reuses it, and final publication refuses any run with a dev result (ADR-0025).
\end{itemize}

\subsection*{What it does not do}
\begin{itemize}
\item It does not replace an AppSec engineer or find every vulnerability.
\item It does not exploit anything live, probe production or run authenticated dynamic tests. PoCs
and fixes are static text; nothing is executed, compiled or applied.
\item It does not certify compliance. OWASP, STIG/SRG and deployment output are worklists and
static observations.
\item It does not treat a missing scan as a pass, or an attack chain as a verified finding.
\item It does not publish a final report without human authorization.
\end{itemize}

2026-09-27/28, and appsec-multi-vuln ran separately. The furthest points were claim review on

\begin{itemize}

roles and sharded pools, lanes 14 and 12b, and dev mode.

units became coverage gaps on Linux.
\item \textbf{Reference data.} No EPSS/KEV snapshot is imported yet (the report says ``not
assessed''). The MITRE feed (brief~O) and exported-symbol entry points (brief~Q) are not merged.

Two search planes serve different questions. The full-text index finds literal text, configuration

report statement back to the exact code or tool output.

\section{Authority and operation}
The machine-readable job graph, design-parity manifest, registry templates and contracts, and
accepted run artifacts are authoritative. The generated job catalog describes the full topology and
the readiness view gives per-job status. This document summarizes them for leadership; it grants no
completion credit. Operators stage the engagement, launch \mono{full\_review}, and follow the
operator guide for commands and stop conditions. Configuration changes belong in versioned registry
templates, contracts, image pins or snapshot policy, never in target content or report edits.
