\begin{bluf}
appsec-review turns an authorized repository snapshot into traceable security evidence and an
evidence-backed draft report. It now includes component-aware search, offline vulnerability
matching, binary hardening, reconciled threat modeling, multi-language SAST, OWASP publication and
synthesis publication. Three integration gates remain before the first final real-target report:
automatic OWASP dispatch-fact derivation, one retained real accepted end-to-end run, and human final
authorization.
\end{bluf}

\subsection*{What leadership should know}
\begin{itemize}
\item Results are evidence-first: every consequential claim must resolve to immutable accepted input.
\item A missing check lowers coverage; it never becomes a clean result.
\item Tools and reference data are pinned, and scanning is offline by default.
\item The produced report is presently a qualified draft until a human authorizes final publication.
\end{itemize}

\section{Purpose and operating boundary}
The system reviews supplied source, build metadata, binaries, images, IaC, dependencies,
configuration, documentation and static exports. Local compilation is allowed to recover compiler
semantics. The baseline does not probe production, call live cloud APIs, run authenticated DAST or
exercise network services. Build scripts are treated as hostile and run in a disposable,
no-network, least-privilege worker. Only allowlisted, hashed artifacts cross back into the trusted
evidence store.

Each job receives explicit, bounded input and emits an immutable attempt with status, coverage,

and revalidate hashes rather than trusting copied prose. The graph allows independent evidence
families to run concurrently, then joins them at explicit rendezvous.

\section{Project partitioning and component model}
Repository discovery separates independently buildable projects, vendored areas, generated code,
deployment surfaces and operational material. Component characterization converts accepted
discovery and evidence into stable component IDs, ownership, languages, trust boundaries, data
flows, build units and coverage. This component map is the shared scope key for threat modeling,
standards worklists, analysis assignments and report rollups.

The full-review input assembler deterministically revalidates the accepted component map, staged
target, source generation and accepted dependency prerequisites. It derives the closed plan,
publishes bounded requests, records absent input classes as \mono{SKIPPED\_NA}, and automatically
dispatches the applicable first wave. It is reinvoked after accepted SBOM, licence and SCA artifacts
exist; the same revalidation opens later licence, SCA, lifecycle and reachability waves without
hand-editing scope.

Reference data is synchronized outside the engagement flow and then bound by digest and timestamp.
This includes Grype/OSV vulnerability data and standards sources. The engagement allows a configured
staleness range; absent or over-age data is reported as a gap. No live lookup is added to the main
flow to make a result appear complete.

\section{Search architecture and cross-references}
Two search planes serve different questions. The full-text and LanceDB semantic projections find
literal text, configuration, documentation and conceptually related evidence. Joern CPG/AST and
LLVM IR projections answer structural questions about calls, symbols, types, control/data flows and
memory operations. Exported records are bounded and preserve source locations and build identity.

Cross-reference edges connect repository partitions, components, files, symbols, build units,
binaries, dependencies, controls, threat hypotheses, claims, findings and report citations. This
lets a reviewer move from a report statement back to the exact code or tool evidence, or from one
component outward to all applicable checks and unresolved gaps.

\section{Threat model and control work}
L6A produces an initial DFD and STRIDE hypothesis set from the characterized components. L6B
reconciles that model with accepted evidence, preserves conflicts and emits explicit model coverage.
Both stages are executable and qualified. A target's report may cite only that target's accepted
reconciliation.

OWASP, STIG/SRG and deployment hardening remain distinct processes:
\begin{enumerate}
\item The OWASP T03--T14 chain routes ASVS/MASVS controls by component, validates bounded work and
publishes deterministic pages, a status matrix, gaps and candidate routes. It is qualified; automatic
derivation of trusted dispatch facts remains open.
\item STIG/SRG tailoring selects platform-specific controls and publishes a validation worklist.
\item Deployment hardening consumes the tailored worklist plus static deployment evidence. Its
observations are not a compliance certification and do not substitute for control validation.
\end{enumerate}

\section{Red, blue and verifier rendezvous}
The orchestrator gives each persona or tool member an immutable handoff, permission receipt and
bounded assignment. Every expected member must reach a durable terminal state. Deterministic merge
validates identity, contracts, citations and order, while retaining dissent. Evidence-qualified
quorum applies evidence and independence thresholds.

Red team proposes attack hypotheses. Blue team attempts to refute, narrow or explain them.
Independent verification alone can verify a claim. Scoring acts only on verified claims. Their
communication occurs through typed, hash-bound artifacts and append-only claim decisions, not an
uncontrolled shared chat. This preserves both the admission head and the later decision head.

\section{Reporting and publication}
The synthesis publication worker consumes exact accepted inputs and produces report JSON and
Markdown, coverage appendix, evidence trace index, publication manifest, LaTeX presentation input,
HTML and render manifests. The fixture-qualified result is correctly labeled
\mono{DRAFT\_EVIDENCE\_BACKED}; it can be \mono{OK\_WITH\_GAPS} and still be an honest successful
publication.

The final gate must revalidate all inputs and presentation hashes, require completion accounting,
and receive human authorization. It may not silently transform a fixture, sample or draft into a
final assessment.

\section{How to operate and configure}
Operators stage the engagement definition, permission grant, target snapshot and any supplied
discovery records; validate graph parity and pins; start Dagster; launch \mono{full\_review}; monitor
accepted attempts and coverage; then launch \mono{synthesis\_report}. Configuration changes belong
in versioned registry templates, contracts, image pins or snapshot policy, not in target content or
ad hoc report edits. The operator guide contains commands and stop conditions.
